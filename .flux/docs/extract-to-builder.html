Extracting the modeling pipeline into Builder

2026-10-27. How the generic capture / spec / 3D / 2D code in 20SPierson fits Builder, and how to move it so 20SPierson is just a project.

1. What each repo actually has

Builder is further along than "a prototype and a plan". Besides prototype/index.html it has a tested Rust kernel (planar B-rep with sticky lines, auto faces, face splitting, push/pull on any planar face, groups, undo journal, .builder JSON format), a wasm wrapper, and a TypeScript app with Line / Rectangle / Push-Pull / Select / Move / Erase tools, an inference engine and the Measurements box, with CI. It is a direct-manipulation modeler: the person draws the geometry.

20SPierson's pipeline is the opposite half: a survey compiler. Geometry is never drawn; it is compiled from measured facts and every number keeps its provenance. About 4,000 lines of Python plus one HTML app:

2. How it fits Builder

Builder's own roadmap already has the slots this code fills: classification attributes on groups, parametric walls/doors/stairs generated by plugins inside components, levels and rooms, images as reference, tags, and "photoreal rendering: export to Blender" (docs/features.md). 20SPierson built those for one real house first. So the pipeline becomes Builder's existing-conditions / survey layer: measured, checked, read-only geometry that the person then designs on top of, by drawing.

The one rule carries over as a product principle

The working method in CLAUDE.md (geometry only from the person's numbers, unknown = MISSING, guesses = ~, conflicts reported never adjusted; the person places, the tool checks) is what makes the survey layer trustworthy. It belongs in Builder's docs as the contract for survey mode and for any agent that edits a spec.

4. Extraction steps

Step 0. Golden master first

Before moving anything, keep today's outputs as the reference: mesh.json, report.md, the .dae, .sh3d contents and bathroom_plan.html, base and each plan. After every step, rebuild 20SPierson and diff. The extraction is done when the diffs are empty (only the house name moves from code to spec).

Step 1. Move the code with its history

# in a scratch clone of 20SPierson
git filter-repo --path model/build.py --path model/blender_build.py --path model/space_plan.py \
                --path measure/ --path-rename model/:survey/src/builder_survey/ \
                --path-rename measure/:survey/src/builder_survey/capture/
# in builder
git remote add pierson ../scratch && git fetch pierson
git merge --allow-unrelated-histories pierson/main

Builder gets survey/ as its own uv project (Python stays Python; Builder already has non-Rust tooling in scripts/). Entry points: survey build, survey render (wraps blender -b -P), survey capture.

Step 2. Make 20SPierson a project

# 20SPierson/pyproject.toml
[project]
dependencies = ["builder-survey", "matplotlib>=3.8", "pyyaml>=6.0"]
[tool.uv.sources]
builder-survey = { path = "../builder/survey", editable = true }
# from 0.1.0:
# builder-survey = { git = "https://github.com/pjsulin/builder", subdirectory = "survey", tag = "survey-v0.1.0" }
uv run survey build --project .                 # was: uv run model/build.py
uv run survey build --project . --plan NAME
uv run survey render --project . -- --render all
uv run survey capture --project .               # was: uv run measure/serve.py

Then delete model/*.py and measure/serve.py / index.html from 20SPierson. measure/checklist.yaml stays (it's house data). Move model/spec.yaml, plans/, space/ to the repo root or keep model/, whichever reads better.

Step 4a. Capture: phone, photo + voice

Order (2026-10-27): after the move into Builder, not before. The model is frozen during the refactor and move; the freeze ends when the move lands, because this step is tested by using the app to change the model.

What actually happened with the measure app: it was used on the phone, not the iPad, because the camera is much better and easier to use, and the per-item form fields were dropped in favour of plain-text answers. So the extracted capture tool should be built around that, not the current form:

  • Phone-first. The native camera (the page's file input already opens it); layout for one hand.
  • Photo + voice note as the unit of record: record audio alongside each photo (or a burst of photos), keep the audio file, and store a transcription next to it in the entry (note.m4a + transcript.txt). Transcription runs on the Mac when the entry arrives (e.g. a local Whisper model through the uv project), so the phone only records.
  • Marks optional. Tap-two-points lines and insets stay available for when a photo needs a pointer, but nothing is required except the photo.
  • No form fields. The checklist becomes a list of open questions with an optional reference photo; the answer is the transcript. Claude takes the plain reading into the spec, citing the entry folder, as today.

6. Recommendation and decisions for you

  • Put the toolkit in the Builder repo (survey/), not a third repo. The .builder exporter and the file format have to change together, and survey mode is a Builder feature.
  • Keep it Python through step 3. Porting the solver to Rust only pays off if you want in-browser regeneration.
  • Order: golden master → move code with history → 20SPierson on the package with identical outputs → .builder export. Steps 0–2 are mechanical and low risk; nothing changes for how you work on the basement.
  • Decided (2026-10-27): the package is builder-survey (command survey). 20SPierson uses it as a local path dependency ({ path = "../builder/survey", editable = true }) until builder-survey 0.1.0, then switches to the git dependency. model/out/ stays committed as today; where outputs go becomes a config option later.
